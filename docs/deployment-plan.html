School Portal Go-Live

What to decide before the portal is deployed for The Educator School System, in what order to do it, and the one choice that matters more than all the others combined.

Next.js 16.3 · Prisma · PostgreSQL Target: 15,000 students + guardians + staff Peshawar, Pakistan

The decision that dominates

Put the application and the database in the same region

This is not a tuning suggestion. On the current setup the application and the database sit in different regions, and I measured what that costs with query logging switched on: every single database query takes about 250 ms, of which the database's own work is negligible. It is almost entirely network time. A page that needs eight queries spends two seconds waiting on the network before it renders anything.

Two rounds of optimisation have already taken the average page from 2.9 s to 1.9 s — caching, removing N+1 relation queries, warming the connection pool. Those were worth doing and they are permanent. But what remains is almost entirely round trips that genuinely have to happen, and no further code change will remove them.

The counter-intuitive part

Distance from the users matters far less than distance from the database. A visitor in Peshawar pays their own network round trip once per page. The server pays its round trip to the database once per query — four to nineteen times for that same page. Co-location is therefore the first constraint; being physically near Pakistan is the second, and a distant second.

In practice this means choosing the database region and the application region together, as one decision, rather than picking a host and then picking a database.

Why a single VPS comes first

At this school's size the workload is small. I sized it from real numbers: the busiest moment of a normal day is roughly 600 teachers marking registers across a 30-minute window, which is a handful of requests per second. The heaviest moment of the year is results day, when perhaps 30,000 people check in one evening — still only tens of requests per second.

That is comfortably within one modest machine. The application is not short of CPU; it is short of proximity to its database. Running Postgres on the same host as the app takes the dominant cost to zero, and it costs less than the managed options rather than more. The price is that backups and updates become yours to run — which is the section further down.

Sizing

What 15,000 students actually costs

Extrapolated from the current database, which holds 269 students and 6,676 attendance records in 17 MB. Growing to full roll is roughly a 56× multiplier on the people and their daily records.

Dimension Today At full roll Comment
Accounts 558 ~31,000 15,000 students, a similar number of guardians, ~600 staff
Attendance rows / year 6,676 ~3,000,000 15,000 students × ~200 school days
Notification rows / year 79 ~1,500,000 A school-wide announcement writes ~31,000 rows by itself
Database size after year one 17 MB ~2–5 GB Small. Disk is not the constraint here.
Uploaded images — ~1–3 GB Logo, building photo, datesheet scans at up to 12 MB each

A machine with 4 vCPU, 8 GB RAM and 80 GB SSD covers this with room to spare. The one number worth watching over time is notification rows, which grow fastest and are the least valuable to keep — they should be pruned after a year.

One thing that must change before real load

Rate limiting currently falls back to an in-memory limiter when Upstash is not configured. On a single VPS that is actually fine, because there is only one process. On any multi-instance or serverless host it is not — each instance would count separately, and the login limit of five attempts per fifteen minutes would silently become five per instance. If the chosen host runs more than one instance, UPSTASH_REDIS_REST_URL and UPSTASH_REDIS_REST_TOKEN are mandatory, not optional.

Pre-flight

Everything that must exist before the first deploy

Setting Why it matters Status
JWT_SIGNING_SECRET Signs every session token. A guessable value means forged sessions for any role. generate fresh
FIELD_ENCRYPTION_KEY Encrypts every CNIC at rest. Losing it makes every CNIC unreadable and every login impossible. generate + escrow
DATABASE_URL Pooled connection. Needs pgbouncer=true if the host is a transaction pooler. per host
DIRECT_URL Unpooled. Migrations hang through a transaction pooler. per host
UPLOAD_DIR Where logos and datesheet scans are written. Must be on a volume that survives redeploys. persistent disk
RESEND_API_KEY + EMAIL_FROM Staff password resets and email 2FA. Without it, emails are only logged to the console. staff only
APP_URL Goes into reset links. A wrong value sends people to a dead address. per host
TLS certificate Session cookies are secure in production — over plain HTTP nobody can sign in at all. required

The encryption key deserves its own sentence

FIELD_ENCRYPTION_KEY is not recoverable and not derivable. If it is lost, every stored CNIC becomes permanently unreadable and every account in the school is locked out — there is no reset path, because the CNIC is the login. It must be written down and stored somewhere separate from the server before the first real account is created. A sealed envelope in the school safe is a legitimate answer.

Execution — each step gates the next

The cutover sequence

Numbered because the order is real: each phase produces something the next one depends on, and each has a condition that must hold before moving on.

01

Provision and pin the region

Stand up the host and the database together, in one region. Confirm the latency before building anything on top of it — this is the assumption the whole plan rests on, and it takes one command to check.

# from the app host, against the real database
psql "$DATABASE_URL" -c "\timing" -c "SELECT 1"

Gate: a trivial query returns in single-digit milliseconds. If it reports 200 ms+, the region pinning has not worked and nothing else is worth doing yet.

02

Secrets, TLS, and the email sender

Generate both secrets fresh on the server, never reusing a development value. Escrow the encryption key off-machine. Point the domain, issue the certificate, and verify HTTPS works before anyone tries to sign in.

openssl rand -base64 48  # JWT_SIGNING_SECRET
openssl rand -hex 32     # FIELD_ENCRYPTION_KEY

Gate: the encryption key exists in a second location outside the server, and https:// serves the welcome page.

03

Schema, and the first principal account

Apply migrations with prisma migrate deploy — never migrate dev, which can reset data. Then seed exactly one account: the principal. No demo data on a production database, ever; it is indistinguishable from real data three months later.

npx prisma migrate deploy
npm run db:seed  # principal + academic year only

Gate: the principal can sign in over HTTPS and reach the dashboard.

04

Set up the school before the people

Academic year, terms, classes and sections, subjects, fee categories, and branding. All of it is enterable through the portal by the principal. Students cannot be enrolled into classes that do not exist yet, so this genuinely has to come first.

Gate: every class the school actually runs exists, with its correct name and section letters.

05

Staff pilot — 20 teachers, two weeks

Create the teaching staff with their class assignments and timetables. Have them mark real attendance, set real assignments, and enter real marks for a fortnight. No students or guardians yet.

This is the phase that finds the problems. Teachers use the app hardest, they are on site to report what is wrong, and nothing they hit is visible to 15,000 families.

Gate: two weeks with no blocking issue, and registers being marked without anyone being asked to.

06

One grade of students and guardians

Enrol a single grade — a few hundred families. Issue credentials through the office and watch what happens at the counter: how long an account takes to hand over, how many people come back unable to sign in, whether the password desk holds up under a queue.

Gate: the office can process the queue without the portal becoming the bottleneck.

07

The rest of the school, grade by grade

Roll forward one grade at a time rather than all at once. Each grade is a fresh chance to stop, and the office workload stays level instead of arriving as one impossible week.

Gate: nothing — this is the end state.

Keeping it

Backups, and proving they work

This database becomes the school's record of attendance, fees and results. Losing it is not an inconvenience; it is a year of paperwork that no longer exists.

  • Nightly pg_dump, off the machine. A backup on the same disk as the database protects against nothing that actually happens.
  • Thirty daily copies, twelve monthly. Corruption is often noticed weeks later, when a report looks wrong.
  • Back up UPLOAD_DIR too. Datesheet scans and the school logo are not in the database.
  • Restore one, on purpose, before go-live. An untested backup is a belief, not a backup. Restore into a scratch database and sign in against it.
  • Store the encryption key separately from the backups. A dump restored without its key is unreadable — which is the point, and also the trap.

What "recovered" has to mean

Write down the answer before you need it: how much data the school can afford to lose (nightly backups mean up to a day), and how long it may be down while restoring. A school can usually tolerate a few hours offline and cannot tolerate losing a term of marks — which argues for frequent dumps rather than a hot standby.

Once it is live

What to watch, and what it means

Signal Where it comes from What it means if it moves
/api/health Built in; point any uptime monitor at it The app cannot reach its database
Page response time Reverse-proxy access log A creep upward is almost always query count, not traffic
Failed logins AuditLog, action LOGIN_FAILED A spike from one address is an attack; a spread is a confusing rollout
Password-desk resets AuditLog, via: recovery-desk High volume means credential handover at enrolment needs fixing
Database size pg_database_size Growth is dominated by notifications; prune beyond a year

The verification suite should run against production once, immediately after go-live, and after every subsequent deploy. It checks the things that are invisible until they are catastrophic — that a parent cannot open another family's records, that a teacher cannot reach a class they do not teach.

npm run typecheck && npm test    # 61 unit tests
npm run check:auth               # every route and action is protected
npm run rbac && npm run smoke   # data scoping · 91 route/role checks
npm run sessions                 # 24h desktop cap · phones stay signed in
npm run recovery                 # password desk cannot be used to enumerate
npm run datesheets               # class datesheets stay inside their class

smoke, sessions and recovery create and delete a temporary probe account. That is safe on production but it does write — run them knowingly, not on a schedule.

Before I execute any of this

What I need you to decide

Nothing above has been done. These are the choices only you can make, and each one changes the steps.

Who will own the server? A single VPS is the best technical answer and the cheapest, but somebody has to apply security updates and confirm the backups ran. If nobody at the school can own that, the managed option is worth its higher price.

What is the domain? It needs to be registered and pointed before the certificate can be issued, and it goes into every password-reset link.

Where does the encryption key live? Name the second location now — not the server, and not the same place as the backups.

How do students and guardians get their credentials? Printed slips at the office is the assumption the app is built around, and the phase 06 pilot is designed to test exactly that. If you had another route in mind, it changes enrolment.

Which grade goes first? Ideally one with engaged parents and a class teacher who will report problems rather than work around them.

When? The start of a term is the natural moment — attendance and fees both begin cleanly, rather than half a term of records living on paper and half in the portal.
